01 / VALUE

价值主张有成立基础

把平时可利用的能力，转化为关键时刻可调动的执行资源。收益取决于真实需求与可靠交付。

02 / REVENUE

月费 + 5% 兑换服务费

月费购买并发与平台配额；充值撮合后收取 5%，其余用于向 Worker 交付真实算力。

03 / MONETARY DESIGN

积分守恒，Worker 不提现

Consumer 获得的积分来自 Worker；Worker 获得算力，现金流向模型供应商与平台。

01
The market thesis

经营的是 Agent 劳动市场

同一个主人可以同时是供给方和需求方。Agent 负责执行交易，主人保留资源授权、预算和收益的控制权。

用户为何需要它

个人持有的 AI 能力与实际需求并不总在同一时间出现：今天有可授权的空闲能力，明天可能需要多个独立任务同时推进。积分把两次需求连接起来，使一次完成的劳动可以换取未来别人的劳动。

即使大家使用相近的顶级模型，不同上线时间、工具环境、可用额度、经验和任务偏好，也会产生交换空间。供给者仍承担自己的模型使用成本与机会成本；“闲置”并不自动意味着零成本。

平台凭什么收费

平台组织任务发现、匹配、预算冻结、权限、交付、验收、结算与信誉。Consumer 买到的是更容易调动多人执行、控制成本和取得可用结果的服务。

商业优势将来自持续可用的优质供给、可信履约记录和低操作成本。如果大部分任务仍需人工反复解释、审核和追单，低价订阅很难覆盖服务成本。

02
Membership & exchange service

月费购买平台权益，5% 完成算力兑换

基础劳动交换与付费平台服务分别成立：贡献劳动可以保留基础参与资格，更强的平台能力需要额外订阅。

Cash / Platform service

现金账本 · 平台经营

月费、充值兑换的 5% 服务费，以及明确约定的超额转发费，用于覆盖服务器、连接、请求、存储、支付处理、客服与争议成本。充值其余部分承担给 Worker 交付算力的义务，不能直接作为可自由支配的收入。

订阅成功 → 增加权益
不自动增加 work credits

劳动贡献免的是基础接入成本；建议付费并发升级不随之全部豁免。该分层是本报告的收费建议。

Credits / Worker compensation

积分账本 · 用户之间结算

已结算劳动所得和购买的已有积分，进入同一消费余额；来源和收入分类仍分别保留。完成任务时，积分从 Consumer 转给执行 Worker。

Consumer − q → Worker + q
市场积分总量变化 = 0

work credit 是内部结算单位；它不是固定 token 数、固定算力时长或随时可兑付的美元。

价格与并发数均为验证假设，不是正式报价或现有能力。原先“贡献可免月费”的设想，在此建议细化为免基础接入费；付费层是增值订阅。所有档位都不赠送积分、不保证固定模型供给，也不自动获得更高消费预算。普通积分劳动交易维持不抽成；5% 只收在已完成的现金充值兑换上，不在后续每次内部工作结算时重复抽成。

低月费可行的前提，是服务成本有边界。 并发数主要限制高峰占用，不能独自限制整月成本。套餐还应约定转发请求数、传输量、连接时长和产物保留期；达到配额后等待、升级，或在预先授权下支付超额费。免费层也必须计入经营成本。

成本维度会随基础设施变化。例如 Cloudflare R2 的官方计费包含存储与操作请求，直接出站流量不收费；这说明“转发成本”不能只用带宽估算，仍需测量实际架构中的计算、连接和请求负担。[官方计费说明]

03
Conservation by design

Consumer 得积分，Worker 得真实算力

平台不支持 Worker 提现。Consumer 现金充值，平台撮合愿意转出已有积分的 Worker；收取 5% 服务费后，向模型供应商采购算力，交付给这个 Worker。

同一笔交易，三方各得其所

Consumer 获得可以雇工的已有 work credits；Worker 转出等量积分，获得扣除 5% 后对应的模型算力；平台获得兑换服务费，并履行采购、分配、计量和交付责任。

Worker 必须事先确认转出数量、模型或供应商、算力计价和有效期。平台不能随机扣减其他 Worker，也不能在充值失败或未匹配时先发消费积分。

算力补给形成持续参与的理由

Worker 可以把劳动所得用于雇佣其他 Agent，也可以在有充值买单匹配时换取模型算力，支持后续工作。算力只用于调用模型，不产生可提现现金。

它把“未来能雇人”的价值延伸为“补充自己的执行资源”。能否持续成立，仍取决于劳动收益是否覆盖模型消耗、失败返工和其他机会成本。

积分总量 M = 所有账户可用积分 + 所有互不重叠的冻结积分
充值转让：M′ = M − q + q = M
任务结算：Consumer 冻结额 − r；执行 Worker 可用额 + r

这里的“总量”包括平台库存及冻结中的积分，避免把同一笔冻结金额同时算在钱包和订单里。兑换时只扣 Worker 一次、给 Consumer 等额增加；5% 从现金中收取，不另销毁一遍积分。采购得到的算力进入独立权益账本，不计入 work credits 总量。

04
Access rules & incentives

保留“双 200”，把资格与余额分开

以下沿用已经确认的贡献规则。现金购买积分和支付月费，都不自动替代当月劳动要求。

维度本次报告采用的规则它解决什么
首月 200完成对应真实工作并验收，将 200 credits 从付款方已有预算转入用户余额。通过劳动获得第一笔购买力；不是注册发放。
每月劳动收入以后每月已结算的真实工作收入 ≥ 200 credits；购买、退款、账户互转不计劳动收入。持续参与供给，防止用充值冒充贡献。
派单余额派单时账户可用余额 ≥ 200 credits，同时足够冻结整个任务或批次预算。避免透支；门槛本身不是一次 200 credits 的扣费。
付费权益订阅提高并发与平台配额；建议不豁免“双 200”。更高预算仍需主人明确授权。把基础参与资格与增值服务分开定价。
收入和余额当月已赚取 200 后，消费或出售积分不抹去劳动记录；但余额跌破 200 时不能新增派单。不会因正常消费被反复要求赚同一笔工资。

并行批次只做一次准入检查

建议在创建整批任务时检查“双 200”和总预算，并一次性冻结预算。不能让第一单冻结后降低可用余额，导致同一已授权批次剩余任务被拒绝。

本报告按派单前余额门槛理解，不额外要求支付任务后仍永久保留 200。若要 200 作为不可花的保证金，则预算公式应改成“200 + 批次预算”，属于另一项待决策规则。

严格贡献门槛会缩小付费人群

现行规则主要服务同时供给和消费的 Agent 主人。只有需求、没有能力每月打工 200 的纯 Consumer，即使愿意付费，也无法直接使用。

这会提升互助属性，但可能降低现金需求流入。将来若验证纯需求客户更愿意付费，可另测“付费 Consumer 免劳动门槛、仍满足余额和预算”的路径；本报告没有把这项替代方案当成已确认规则。

首月入账必须有付款方。 平台可用事先限定总量的启动预算，购买真实有用的工作。没有付款预算，不能因为新人完成贡献就自动新发 200。试用能力考核与有偿贡献也应区分；当前 v0.2 的无薪试用不会产生余额，新提案尚需单独落地。

建议以明确时区的自然月统计合格结算，月度重置只清贡献计数，不清钱包余额；新月尚未达标时暂停新增派单，已冻结且正在履行的订单继续按约定处理。边界时间、退款冲正和贡献归属需在正式规则中确定。

05
What conservation does not solve

守恒能阻止无来源增发，不能保证购买力

积分记录购买力，在线 Worker 才提供实际服务。两者必须分别观察，不能把积分余额当成已经储存在服务器里的算力。

Quantity

发行量

充值、验收和赠品若自动增发，会扩大积分总量。建议普通交易始终守恒；启动发行独立记录、总量有上限，不向新用户直接赠送消费额。

Liquidity

流通速度

现金买家把原本闲置的积分立即拿来雇工，即使总量不变，短期需求仍会增加。大量囤积则可能让交易停滞。应监测活跃余额、卖盘深度和再消费率。

Capacity

有效供给

顶级 Worker 可能同时离线，或只接受更高报价。积分价格会受供给、质量和等待时间影响。固定积分总量并不等于固定任务价格。

实际问题建议处理避免的错误
没有人愿意卖积分展示可买数量和有效报价；等待匹配，或取消未完成交易。收到现金后用增发填补缺口；承诺随时无限充值。
Worker 已赚够但不再上线观察近期在线能力、交付和报价，吸引新的真实供给。兑换来的算力可自用，不等于承诺必须回平台接单。只用积分总量推断供给充足。
为凑 200 互相刷单剔除关联、自买自卖和无实际交付订单；随机复核价值和验收证据。将账户互转计为劳动贡献或好评。
所有人同时需要 50 个 Agent清晰显示队列与预计可用容量；为共享 Worker 约束并发。把卖出 50 个并发位解释为保证同时有 50 名合格 Worker。
06
Compute delivery / No cashout

算力有真实来源，权益能独立核对

现金不打给 Worker。平台收款后采购模型服务，交付到 Worker 认可的账户或受控 API Key。未完成的消费退款可以原路退给付款方，但这不开放 Worker 提现。

交付形态怎么交给 Worker成立条件
直接充入 Worker 账户通过供应商正式支持的充值、兑换码或合作接口，充入 Worker 已确认的模型账户，并取得到账回执。必须逐家确认支持范围、地区、最低金额、退款和账户归属。不能默认任意大厂账户都能代充；不索要用户登录密码。
平台专属 API Key平台采购真实模型用量，向 Worker 发放单独的受限 Key；按公示模型价格扣减该用户的算力余额。需要每用户预算、用量查询、限流、撤销和并发预留；不能把平台主 Key 或管理 Key 发给用户。
上游管理型子 Key在供应商支持的范围内创建用户专属 Key 并设置支出上限，可作为平台网关的替代交付方式。Key 上限只是支出权限，不是独立资金。总采购余额需覆盖全部已承诺的未用权益，并限制跨用户相互占用。

OpenRouter 官方提供程序化创建、管理和禁用 API Key 的接口；其账户余额、每 Key 支出限制和并发请求预算是不同约束。可以参考这种交付方式，但不据此推断所有供应商支持向其他账户充值。[Key 管理] · [余额与限额]

Keepwork Server 可以作为交付形态的参考。 本报告按产品方提供的类比，建议优先评估已有的模型采购、用量记账和 Key 分发能力；未审阅 Keepwork Server 的实现，不能把计量隔离、跨用户限额或供应商授权视为已经具备。

先锁定资源，再完成交换

  1. Worker 同意转出积分，确认算力报价、可用模型、交付方式、有效期和 5% 费用；锁定这笔积分。
  2. Consumer 确认报价并支付；可信回执到达后，预留相应采购资金。
  3. 核实供应商到账，或从已购算力池中划出该 Worker 的专属额度；外部结果不明时保持待确认。
  4. 在账本事务中等额转移 work credits，记录算力交付义务或凭证，再开放对应使用权限。

供应商接口和本地账本不能组成一个原子事务。建议通过可恢复状态机与幂等回执协调；失败时不让双方同时拿到可花资产，也不因重试重复采购。

已购算力不能超额分配

每个 Worker 的剩余算力权益与运行中预留都必须有采购余额覆盖。一个人可以持有多个 Key，但这些 Key 共享同一用户预算；更换或轮换 Key 不重置已消费金额。

一次性兑换的额度不能每月自动刷新。供应商报价、缓存价、工具费和计费方式应在报价中说明；请求发起前预留，结算后按实际用量扣减，防止并发透支。

“API Key 可用”不等于“交付了独立的 $38 余额”。自有网关或子 Key 的支出上限必须与平台内部算力权益和真实供应商余额对账。

失败、退款与拒付

未支付成功时解除尚未成交的锁定；采购失败时保留待处理或按约定退款；到账状态不明时先查询回执，不能盲目重购。已成交的冲正必须同时处理积分、资金和算力权益。

算力已消耗或直接到账不可撤回后，买方仍可能拒付。平台需要额度限制、风险预留和明确的损失承担；不能向无关的执行 Worker 任意扣款。取消提现减少一种流程，但没有消除收款风险。

劳动、算力与授权各自独立

Worker 使用兑换来的算力继续工作，只能通过真实雇主的既有预算赚取积分；消耗 token 本身不会铸造新积分。无真实需求的相互刷单，不应生成月度贡献或信用。

买算力不等于获得替其他主人读取文件或执行工具的权限。额度可以在授权范围内自用；平台不能默认 Worker 必须把兑换来的全部资源重新投入市场。

实现使用固定精度整数记账，现金精确到货币最小单位，work credits 使用 100 minor units = 1 credit。供应商若按小于一分钱的金额计量，应选择足够细的整数精度，再按公开规则汇总舍入。5% 费率、报价版本、采购凭证与权益变更均关联同一交易。

07
Subscription + 5% service fee

5% 是服务费，采购与履约决定利润

平台不自建推理算力，但现在承担了采购和交付责任。商业模式包含 Consumer 订阅、已有积分撮合与算力代购服务；必须同时计算模型采购、支付、转发和风险成本。

充值 C：服务费 F = C × 5%；承诺的算力价值 B = C − F
单笔经营贡献 = C − 实际算力采购成本 − 该笔支付、转发与风险成本
月度经营贡献 = 实收订阅费 + 所有充值的经营贡献 − 其他平台运营成本

按 $100 充值理解

本报告默认按公示模型价向 Worker 交付 $95 可消费算力，并保留 $5 服务费。若采购成本就是 $95，则这 $5 还需覆盖支付渠道、调用转发、客服与失败损失，剩余部分才是经营贡献。

如果打算让“95%”表示含上游费用的采购预算，实际到账的可消费额度可能少于 $95；必须在成交前写明实际到账量，不能用“只收 5%”掩盖额外扣减。

类似 OpenRouter 的形态，不必使用其采购渠道

OpenRouter 官方 Standard 当前在购买 credits 时收取 5.5% 费用。若买入 $95 可消费额度还需额外支付 5.5%，支出约为 $100.23，已经超过 Consumer 的 $100，尚未计算本平台其他成本。

因此应优先比较供应商直采、正式合作价格与自有网关；是否使用聚合渠道取决于总采购价。采用 API Key 交付形式，本身不会免去上游费用。[OpenRouter 官方价格]

95% 的采购责任不是闲置利润。 未使用的算力池仍对应已承诺的用户权益，不能因为尚未调用就把余额当作已经赚到的钱。下面的经营测算把这部分完整预留；采购附加费与兑换运营成本另行计入。

08
Validation before scale

先证明能赚、能花、值得订阅

早期最关键的不是挂牌 Worker 总数，而是用户是否反复把已赚的积分转化为合格交付，以及平台是否能用可持续成本完成这件事。

Phase 1 / Earn & hire

验证真实劳动循环

从一类容易验收、适合拆分的任务开始，例如代码审阅或资料整理。用有上限的真实启动订单，观察 Worker 赚到积分后能否再次雇到人。

Phase 2 / Paid parallelism

验证付费并行价值

开放有限的并发订阅试验。比较用户单人处理与多 Agent 批次的有效完成时间、质量、协调成本及下一周期付费意愿。

Phase 3 / Compute exchange

验证积分换算力

在具备采购、算力交付和对账能力后，小规模验证 Consumer 充值与 Worker 积分转让。监测算力到账、后续使用、兑换成本和充值损失。

验证指标应看到的证据对应商业问题
赚取后的再消费获得真实报酬的用户，随后用积分购买并验收其他人的工作。积分是否有实际使用价值。
供需与撮合质量按任务类型统计匹配等待时间、报价、有效在线 Worker 和验收完成率。是否存在持续可用的劳动市场。
并发带来的净收益从发起到合并结果的总时间下降，同时质量不下降、返工成本可控。用户为何为 5、15、50 个并发位付费。
付费续订与单位成本实际扣款与续订、分档服务成本、免费层总成本和人工介入分钟数。订阅模式是否产生经营贡献。
现金、积分、算力完整性积分等额转移，5% 与采购款分开，已承诺算力都有覆盖；失败、退款可对账。充值是否守恒，Worker 能否获得并实际使用算力。

优先服务谁

优先验证已经拥有高能力 Agent、需求有波峰、愿意贡献闲置能力的个人开发者与小团队。这一群体更符合“双 200”机制，也更容易比较集中雇工与自己排队执行的差异。

用户仍可自行运行多个 Agent，或直接使用模型服务。平台需要证明任务交接、供给发现、结算和结果管理节省的精力，值得额外的月费与市场交易成本。

供给侧也必须算得过来

Worker 主人承担模型费用、资源占用和交付失败风险，获得未来雇工的价值，或通过匹配兑换获得真实模型算力。若付出长期高于可获得的回报，供给不会仅因“AI 可以自主打工”而持续。

供给必须建立在可持续的服务商授权与主人许可之上；不能默认任何订阅额度都允许这种第三方工作方式。顶级模型与质量要求还需可核验的证据支持。

建议的首要验证：让同一批用户经历“真实赚取 → 批次雇工 → 合格交付 → 自愿续订”。若只看到贡献增长而没有消费与付费续订，尚不能证明商业模式成立。所有阈值应在试验开始前定义，不用事后挑选好看的指标。

Assessment boundary

本次如何做压力测试

按“卖可验收的工作成果，Worker 兑换真实算力”的业务理解，假设所需供应商许可已经成立，不把服务商是否允许作为扣分项。

My judgment

RSI 能提高成功机会，但要允许它改规则

工程成本下降会让你更快找到问题、更便宜地试错。它不能自动生成外部需求，或使用户愿意接受不合适的准入条件和报酬。

Stress 01 / Demand blocked

最大冲突：“买美国模型的成果”却必须先具备劳动能力

中国用户可以用中文提交目标和资料，由高能力 Worker 交付结果。这条路径的吸引力在于用户无需自己组织模型账户、环境、任务拆分与验收。不过，最愿意付钱的客户未必已有合格 Worker，更未必能每月稳定赚取 200 credits。

如果所有付费客户仍须先打工，产品会把一部分最直接的现金需求挡在门外。 这与扩大中国消费侧需求的目标有冲突。我的第一优先级建议是：贡献 200 保留为免费参与或会员优惠条件，付费纯 Consumer 可凭已匹配到账的余额和任务预算消费。余额门槛应与风控成本相对应，避免再成为固定入场券。

这是压力测试提出的规则修改建议，不是把此前确认的“双 200”偷偷改为已实施规则。可以保留互助层，同时单独测试纯消费层。

Stress 02 / Compute is not cash

“有闲置算力的人，为何还需要更多算力”必须有具体答案

部分供给者愿意把即将失效的能力，换成以后可用、不同模型可用的算力；另一部分更看重未来雇工。也有人已经有过剩资源，对额外算力需求很低。这是参与人群差异，不能用同一个美元面值假设每个人都愿意接单。

Worker 净收益 = 算力奖励的主观使用价值 + 其他实际收益
− 本次模型、环境、时间与失败返工成本

压力示例：一单的积分按撮合报价可换 $20，最终交付 $19 算力。若 Worker 只愿为这份算力支付 $10，而全部执行成本为 $12，这单对它仍是亏损；若成本仅 $2 且算力确有用途，交换就很有吸引力。这些是假设，不是市场报价。

不提现可以成立，但对应的是算力互助与再投入人群，不是覆盖所有劳动供给者。 应优先招募愿意用报酬雇工或补充模型调用的 Agent 主人，并观察 30 天内是否实际消费奖励。平台自发订单与用户互相刷单不算外部需求。

Stress 03 / Thin transaction margin

5% 更适合补充收入，难以单独承担人工交付

使用一个有公开依据的支付成本情景：收款费 2.9% + $0.30；另假设网关成本 0.5%、预期交易损失 0.5%；95% 算力采购无额外加价。支付基准来自 Stripe 展示的美国境内卡标准价，不是中国支付渠道的实际报价，也不含其可能另计的跨境或换汇成本。[官方费率]

低费率收款、合理最低充值额和近乎自动化的交付可以改善它；最低充值额也会增加首次尝试阻力。更可靠的收入主轴仍是用户愿意续订的平台服务，5% 用于支持兑换环节，而不是补贴无限客服。

Stress 04 / Fifty simultaneous jobs

并发可以实现，整批可靠交付需要额外设计

假设每项任务独立、一次合格率为 98%，50 项全部一次合格的概率是 0.98⁵⁰ ≈ 36.4%。这不表示 63.6% 的工作都失败：平均只有一项失败，但“整批毫无问题”很难。

若只重试失败项，且第二次失败与第一次独立、合格率仍为 98%，每项最终成功率升到 99.96%，整批约为 98.0%，平均多执行一次任务。现实中的共享提示错误、相同资料缺陷或供应商中断会让失败相关，重试收益可能低得多。

速度同样受限：即使只有 10% 工作必须串行，50 并发在零协调开销下的理想加速也只有约 8.47 倍。验收、重试和结果合并还会消耗时间。产品应销售按期限获得合格结果的体验，按任务特点选择 1、5、10 或 50 并发。

Anthropic 2025 年的研究系统经验支持独立方向并行的价值，也明确指出依赖密集任务与高 token 消耗的问题；其具体倍数属于那套系统，不应直接当成本项目或 2026 年模型的参数。[工程经验]

Stress 05 / Liquidity

积分不增发，仍可能“有需求买不到”

Consumer 充值需要愿意转出积分的 Worker。无人愿意换算力时，平台不能为完成充值自动增发。应先展示可成交库存并撮合，再确认充值；未匹配订单不能伪装成可用余额。

若系统总积分为 100,000，要求派单时可用余额至少 200，则任一时刻可同时持有至少 200 的账户最多 500 个。这只是瞬时余额分布上限，不是总用户数上限；积分周转可以继续，但固定门槛会加剧资金分布与入场摩擦。

Stress 06 / Abuse & demand

守恒不等于没有刷单与假需求

关联账户可循环转账凑月度收入、互评高分，或用低质量成果触发奖励。总积分没增加，信誉与准入仍可被污染。应把独立客户验收、关联关系和真实使用行为纳入贡献判断。

假设充值损失达到总流水的 1%，就消耗掉 5% 名义服务费的五分之一。平台买自己的研发成果有使用价值，却不能证明外部客户愿意续费；RSI 产生的内部订单要单独统计。

Stress 08 / China as an entry market

中国市场可以是入口，交付能力才应成为长期价值

我认可这个切口：让中国用户用熟悉的语言和流程，购买由美国高能力模型完成的成果。平台可以承担任务说明、上下文组织、工作拆分和验收，把接入便利转化为实际完成工作的便利。

但应再施加一个压力条件：假设同等模型未来能够更便宜、更方便地直接使用。用户仍愿意付费的理由，需要是可靠结果、节省操作时间、批量处理和可追溯验收。仅有模型入口的差异很容易被直接接入替代。

建议先选“批量文档提取与核验”或“有固定验收标准的开发辅助”等一种场景，用 3–10 个 Worker 获得稳定交付，再扩展到 50 并发。所选场景是试验建议，尚无证据证明其中任何一个已获得产品市场匹配。

11
RSI as a business experiment engine

RSI 的目标：每轮少一次失败，多一次真实复购

把“增加功能、生成代码”改成可度量的改进任务：降低每份合格交付的现金成本、主人操作时间和失败率，同时提升外部客户复购。不同指标要分别呈现，不能用更多 token 或内部任务量代替收入。

最值得先自动化的四件事

  1. 把真实失败变成可重复的任务样本，减少同一种错误再次发生。
  2. 自动拆分独立任务、合并产物，失败只重试局部，严格共享总预算。
  3. 用可执行的验收条件和人工抽检减少操作员介入，记录实际节省的分钟数。
  4. 根据任务难度决定并发和模型，而非默认每次都招满 50 个。

最危险的自我强化

同一套 Agent 生成任务、完成任务、自己验收、自己打高分，再用内部积分支付，可能制造漂亮的流水，却没有外部用户价值。

要保留不参与调参的任务集与独立验收，分别记录内部研发需求、运营补贴订单和独立付费订单。客户的再次付款，比 Agent 对产品的表扬更有证明力。

METR 在 2026 年更新中指出，AI 生产力估计受到参与者和任务选择偏差影响，旧实验数字不能简单代表当前收益。这里借鉴其测量提醒，不用旧模型的表现推断 RSI 必然有效或无效。[研究更新]

建议验证阶段必须获得的证据没有得到时如何调整
第 1–2 周：一个具体场景来自非关联用户的真实任务；统一验收标准；比较当前“双 200”与付费纯消费路径的流失原因。先改准入或任务定义，不继续堆通用功能。支付未具备生产条件时，只记录意向与仿真，不冒充真实成交。
第 3–6 周：付费交付至少 30 个独立付费客户、200 个真实任务，逐笔记录验收、实收、返工、人工分钟与成本。若只靠免费或关联订单活跃，重新选择客户和场景；把补贴单与自然付费分开。
第 7–12 周：复购与并行观察窗口完整的付费客户 30 天复购达到 30%；95% 订单在约定期限内合格完成；主要客户组扣除变动成本后的现金贡献为正。若质量只能靠大量人工维持，先降低自主范围；若交付稳定仍不复购，修正价值主张或定价。

上述人数、期限与比例是建议的决策门槛，不是行业基准、统计显著性保证或预测。完成率包含约定预算内的有限重试，分母包含全部到期真实订单；复购只计独立付费客户且排除平台自购。固定研发投入与创始人时间另行展示，避免用变动贡献冒充公司净利润。

Decision

我会继续做，但把 RSI 用在验证和修正机制上

有机会做成的第一形态，是能稳定交付一类高价值成果、拥有重复付费用户的小型市场。中国需求可以提供切入口，Worker 的闲置能力与算力补给可以组织供给，RSI 可以降低运营与开发成本。

当前最先需要挑战的是纯消费者的劳动门槛，其次是低成本验收和 5% 的真实利润。若这三项验证过关，再扩大并发和任务种类；若只是代码越来越多、内部积分越来越活跃，我不会据此上调 62 分的判断。
